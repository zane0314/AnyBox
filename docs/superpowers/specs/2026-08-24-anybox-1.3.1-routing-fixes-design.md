# AnyBox 1.3.1 应用路由与分流检测修复设计

## 1. 文档状态与执行边界

- 本文档定义 AnyBox 1.3.1 的应用路由配置与分流检测修复方案。
- 产品行为唯一基线为 `AnyBox_1.3.0.apk`，其 versionCode 为 249、versionName 为 1.3.0。
- 目标版本为 versionCode 250、versionName 1.3.1。
- 本轮工作只编写设计文档，不修改应用代码、不构建 APK、不运行模拟器。
- 后续设计、实施、排障和验证均由当前主代理内联完成，明确禁止调用子代理。
- 后续实施中若发现本文未覆盖的新问题，处理结果必须以 1.3.0 的效果为准；除本文明确修复的路由问题外，1.3.0 的已有效果不得变化。

## 2. 已确认问题

### 2.1 分流检测入口破坏页面布局

1.2.5 调试实现通过 `root.addView()` 向智能分流页面根布局直接加入一个可点击 `TextView`。模拟器实测中，该控件竖屏边界为 `[0,0][1080,136]`，覆盖系统状态栏，大部分区域无法正常点击；横屏边界为 `[136,0][2400,136]`，仍覆盖顶部并破坏页面布局。

该入口不是应用现有的菜单项、MaterialButton 或 LiquidGlass 卡片，颜色、尺寸、语言和无障碍语义均与 1.3.0 UI 不一致。

### 2.2 检测对话框与 1.3.0 风格不一致

旧实现使用原生 `android.app.AlertDialog`，并把 30 个预置域名逐个显示为全宽按钮，导致对话框过长、信息密度低。所有文案硬编码为中文，无法跟随应用语言；控件也未复用 1.3.0 的 Material 主题。

### 2.3 默认配置下检测不可用

旧实现固定查询 `http://127.0.0.1:9090/connections`，但未检查 Clash API 开关。默认关闭 Clash API 时，检测直接显示连接 9090 失败的底层英文异常。手动开启开关后还必须重连 VPN，9090 才会监听；旧实现没有提供该前置检查和明确操作。

### 2.4 Clash API 可用后仍找不到连接

模拟器确认 9090 已监听后，检测 `chatgpt.com` 仍返回“无法确定分流：未找到唯一连接记录”。旧实现仅通过 SOCKS 建立到 `domain:443` 的 TCP 连接，不发送应用数据，随后只查询一次 `/connections`。该流程不能保证 bundled sing-box 已创建并暴露可匹配记录。

此外，旧实现要求一次查询恰好得到一条记录，没有短间隔重试；时间解析只支持无小数或三位毫秒；域名、源端口和时间任一字段出现兼容差异都会直接失败。

### 2.5 生命周期和资源处理不完整

- `cancelled` 标志会被设置，但后台任务不读取该标志。
- 页面关闭或旋转后，后台线程仍可能尝试更新已销毁控件。
- `HttpURLConnection` 只在成功路径断开，异常路径可能不释放资源。
- Mixed Inbound 关闭时仍读取本地 SOCKS 端口，没有明确兼容检查。
- 底层异常原文直接显示给用户，错误信息中英文混杂。
- 旧设计要求的最小连接筛选自检未实现。

### 2.6 应用代理/绕过与智能分流存在捕获范围冲突

1.3.0 的 Android VPN 捕获范围由“分应用代理”设置先决定：

- “仅代理所选应用”通过 `VpnService.Builder.addAllowedApplication()` 只捕获设置名单。
- “绕过所选应用”通过 `addDisallowedApplication()` 排除设置名单。

智能分流应用规则随后才由 sing-box 的 `package_name` 路由规则处理。若某个智能分流应用未被前一层 VPN 捕获，流量根本不会进入 sing-box，智能分流规则无法生效。具体表现为：

- 仅代理模式下，智能分流选中的应用不在全局代理名单时会完全绕过 VPN。
- 绕过模式下，同一应用出现在绕过名单时也会完全绕过 VPN。
- UI 允许用户为应用选择智能分流策略，但没有说明或修复这项前置冲突。

这是 OS 级 VPN 捕获与核心级路由规则之间的管线问题，不能通过增加另一套静态规则匹配器解决。

## 3. 目标

1. 将“分流检测”改为符合 1.3.0 UI 和交互规范的低频诊断工具。
2. 使用真实代理连接和 Clash API 证据显示本次连接的规则、出口链和目标 IP，不静态推测结果。
3. 统一应用捕获语义，确保已启用的智能分流应用能够进入 VPN 并执行对应路由规则。
4. 保留用户原始应用代理/绕过名单，不在后台暗中改写设置。
5. 保证除本文明确范围外，1.3.0 的功能、界面和路由顺序不变。

## 4. 非目标

- 不修改或重新设计 1.3.0 的节点、订阅、规则更新、DNS、全局模式和节点选择。
- 不改变用户高优先级路由规则、智能分流规则和普通用户规则的既有相对顺序。
- 不实现第二套路由匹配器，不解析 `.srs`，不使用系统 DNS 结果冒充实际连接 IP。
- 不自动判断某个分流结果是否符合用户预期，只展示核心运行证据。
- 不保存检测历史，不做后台监控或批量检测。
- 不升级 sing-box、libgojni、Android SDK 或第三方依赖。
- 不调用子代理。

## 5. 路由架构与优先级

### 5.1 总体管线

```text
Android VPN 有效捕获范围
        ↓
用户自定义高优先级路由规则
        ↓
智能分流应用/域名规则
        ↓
普通用户路由规则
        ↓
主节点或默认出口
```

1.3.1 只修正第一层“有效捕获范围”的输入集合，不改变后续 sing-box 规则构建顺序。

### 5.2 有效智能分流应用集合

定义 `S` 为当前连接中所有“实际启用”的智能分流应用包名集合。只有同时满足以下条件的应用才进入 `S`：

1. 当前运行模式支持智能分流，且智能分流快照处于启用状态。
2. 应用所在内置组或自定义组的策略不是“关闭”。
3. 该组能解析到有效出口；沿用 1.3.0 对无效选择回落到默认出口的规则。
4. 包名来自 1.3.0 现有 `SmartRoutingSnapshot.packagesFor()`，不建立新的应用目录或名单存储。

全局模式开启、智能分流整体未生效或组策略为“关闭”时，该组不贡献包名。一个应用出现在多个启用组时，只在 `S` 中保留一次；最终命中哪个智能规则继续由 1.3.0 现有规则顺序决定。

### 5.3 有效 VPN 捕获集合

设用户在“分应用代理”中保存的名单为 `U`：

| 设置状态 | 1.3.1 有效行为 |
| --- | --- |
| 分应用代理关闭 | 捕获全部应用；智能分流按 1.3.0 规则匹配 |
| 仅代理所选应用 | 允许列表为 `U ∪ S` |
| 绕过所选应用 | 排除列表为 `U - S` |

该合并只用于本次 `VpnService.Builder` 配置，不修改 DataStore 中的 `proxyApps`、`bypass` 或 `individual`，也不改变应用管理页面显示的用户原始名单。

智能分流应用因此优先获得“进入 VPN”的资格，但进入 VPN 后仍服从 1.3.0 的用户高优先级规则、智能分流规则和普通用户规则顺序。该优先级不等于强制指定最终节点。

### 5.4 配置变化生效方式

沿用 1.3.0 的连接生命周期：会影响 VPN 捕获范围或核心配置的设置，在重新连接或现有 reload 流程执行后生效。设计不增加独立常驻服务，也不在应用选择时暗中重建 VPN。

## 6. 分流检测界面

### 6.1 入口

- 在 `smart_routing_menu.xml` 中增加“分流检测”菜单项。
- 入口与“全局模式”同处智能分流页面右上角更多菜单，`showAsAction="never"`。
- 删除旧版根布局顶部动态 `TextView` 及其 `root.addView()` 调用。
- 菜单标题、对话框标题、按钮、状态和错误文案均使用中英文字符串资源。

分流检测是低频诊断工具，不新增页面常驻卡片，也不占用智能分流主内容区域。

### 6.2 对话框

- 使用 1.3.0 已包含的 `MaterialAlertDialogBuilder` 和 SagerNet/AnyBox 对话框主题。
- 使用标准域名输入框，默认可为空，不自动触发网络操作。
- 30 个预置域名保留原分类和内容，但改为分类下拉选择；选中后填入域名输入框。
- 显示单次检测结果；再次检测覆盖旧结果。
- 提供“开始检测”和“关闭”。检测过程中禁用开始按钮并显示进度状态。
- 控件使用标准按钮/菜单语义，支持 TalkBack；竖屏、横屏和窗口尺寸变化均不得覆盖状态栏。

## 7. 分流检测数据流

1. 规范化输入：去除首尾空白并转为小写，只接受合法主机名；拒绝 URL、端口和 IP。
2. 检查 AnyBox VPN 是否处于已连接状态；未连接时不自动连接。
3. 检查 Mixed Inbound 是否可用；关闭时说明检测依赖本地 SOCKS，不自动改变设置。
4. 检查 Clash API 设置和 `127.0.0.1:9090` 可达性。
5. Clash API 关闭时提供“启用并重连”；只有用户明确确认后，才调用 1.3.0 现有设置和服务重载流程。该开关状态会保留，并在提示中说明可从设置关闭。
6. 记录开始时间，通过当前本地 SOCKS 端口连接 `domain:443`；目标必须使用 unresolved host，确保核心接收域名。
7. 在 SOCKS 连接上发起最小 TLS 握手并携带目标域名 SNI，使 bundled sing-box 产生有实际数据的可观察连接。HTTP 页面状态和业务响应不参与路由结论。
8. 保持 TLS/Socket 存活，在总计 8 秒的截止时间内短间隔轮询 `/connections`；轮询由截止时间控制，不使用单次查询或无上限重试。
9. 使用规范化域名、临时 Socket 源端口和开始时间筛选连接；时间比较兼容 RFC3339 的不同小数精度和时区格式。
10. 找到唯一记录后读取 `metadata.destinationIP`、`rule`、`chains` 和连接状态，并显示总耗时。
11. 若核心未提供 `destinationIP`，显示“核心未提供目标 IP”，不得用 Android DNS 补齐。
12. 成功、失败、取消、关闭页面或配置变化后均关闭 TLS Socket、底层 Socket、输入流和 HTTP 连接。

## 8. 结果与错误定义

### 8.1 成功结果

只显示以下事实：

- 域名。
- 实际目标 IP 及 IPv4/IPv6 类型；核心未提供时明确说明。
- 命中规则。
- 出口链和最终节点。
- 连接状态与耗时。

### 8.2 错误分类

- 域名无效：不发起连接。
- VPN 未连接：提示先连接 VPN。
- Mixed Inbound 关闭：说明依赖，不自动开启。
- Clash API 关闭：提供经确认的启用并重连操作。
- Clash API 已启用但 9090 不可访问：提示控制接口不可用。
- TLS/SOCKS 超时：在 8 秒截止时间内取消并释放资源。
- `/connections` 始终为空：提示核心未产生可观察连接记录。
- 存在候选但条件无法唯一匹配：提示匹配记录不唯一，不选择任意一条。
- API JSON 缺字段或格式异常：显示可理解的控制接口响应错误。
- 页面关闭或旋转：取消当前任务，不向已销毁控件投递结果。

用户界面不直接显示 Java/网络底层英文异常。安全日志可记录异常类型和不含节点、订阅、凭据的简要原因。

## 9. 生命周期、并发与资源约束

- 同一对话框同一时间最多执行一个检测任务。
- 任务必须在连接、轮询和 UI 投递前检查取消状态。
- 对话框关闭、Fragment View 销毁和配置变化均触发取消。
- 任务结束后恢复开始按钮状态，但仅在对应 View 生命周期仍有效时更新 UI。
- `HttpURLConnection.disconnect()` 和所有 Closeable 必须放在统一清理路径。
- 轮询使用单一截止时间，不叠加多个 8 秒超时导致总等待无限延长。
- 不创建 Service、数据库、历史表或新的后台线程池；复用 Java/Android 原生能力和应用已有生命周期。

## 10. 最小实现边界

后续实施以 1.3.0 解包工程为起点，预计只涉及以下现有边界：

- 智能分流菜单资源及中英文字符串资源。
- `SmartRoutingFragment` 的菜单处理。
- 一个集中负责检测 UI、连接、轮询、解析和取消的维护源模块及其生成 Smali。
- 现有 VPN 捕获集合构建位置，复用 `SmartRoutingStore`、`SmartRoutingSnapshot.routingGroups()` 和 `packagesFor()` 计算 `S`。
- 版本元数据。

不得把 1.2.5 整个工作树覆盖到 1.3.0，不得复制第二份智能分流快照、应用目录、配置生成器或 VPN 服务。

### 11.3 模拟器手工路由矩阵

使用两个测试应用 `A`、`B` 和一个已启用智能分流组，逐项手工操作并核对生成配置、VPN 捕获结果与实际连接：

| 场景 | 设置名单 | 智能分流 | 预期 |
| --- | --- | --- | --- |
| 分应用关闭 | 任意 | A 启用 | A、B 均进入 VPN；A 命中智能分流 |
| 仅代理模式 | 仅 B | A 启用 | A、B 均进入 VPN；A 命中智能分流 |
| 仅代理模式 | 仅 B | A 关闭 | 仅 B 进入 VPN |
| 绕过模式 | A、B | A 启用 | A 进入 VPN 并命中智能分流；B 绕过 VPN |
| 绕过模式 | A、B | A 关闭 | A、B 均绕过 VPN |
| 全局模式 | 任意 | A 原有选择 | 智能分流不扩展捕获范围，行为与 1.3.0 全局模式一致 |
| 多组包含 A | 任意 | 两组启用 | A 只进入一次 VPN；按 1.3.0 规则顺序命中 |

测试后确认用户保存的应用代理/绕过名单没有被改写。

### 11.4 模拟器手工分流检测

- 右上角更多菜单可进入检测对话框，页面顶部无额外控件。
- 竖屏和横屏不覆盖状态栏；主题、暗色模式和语言跟随 1.3.0。

- 至少检测一个国内域名和一个国外域名。

## 13. 风险与回退

- bundled sing-box 若不在 `/connections` 暴露 Mixed Inbound 连接，后续必须先用最小日志确认边界；不得增加静态规则推测作为伪成功回退。
- TLS 握手可能因站点、网络或节点失败。此类失败应报告连接阶段，不得伪装为路由错误。
- Android VPN allow/disallow 列表只在 VPN 建立时生效；测试必须包含重新连接，避免把旧 TUN 状态当成新配置。
- 若智能分流有效集合在运行时无法从现有快照稳定取得，应停止实现并回到设计评审，不得复制第二套状态。
- 回退方式是恢复 1.3.0 基线 APK 和原始数据；设计不迁移或破坏用户保存的应用名单，因此不需要数据回滚脚本。
