# AnyBox 1.3.3 sing-box 1.13.19 整包核心升级设计

## 1. 文档状态与执行对象

- 本文档定义 AnyBox 1.3.3 的唯一实施方案：保持 1.3.2 全部功能、数据和界面行为不变，将内置定制核心升级为基于官方 sing-box `v1.13.19` 稳定源码构建的兼容核心，并重新打包完整 APK。
- 本文档面向 Luna 直接执行。Luna 必须先读取本文和项目根目录 `.ai/HANDOFF.md`，再核对实际文件、Git 差异、工具链和模拟器状态；交接内容只用于导航，实际文件和实测结果优先。
- 1.3.2 是唯一行为与数据基线。除版本元数据和本文明确要求的核心替换外，不得修改、删除、隐藏、重命名或重新解释现有功能。
- 目标包名固定为 `com.zane.proxy`。
- 目标版本固定为 versionName `1.3.3`、versionCode `252`。
- 目标交付文件固定为无调试后缀的 `AnyBox-1.3.3.apk`。
- 本文档批准的是整包升级，不是运行时核心更新器。不得添加“下载核心”“切换核心”“热更新核心”等界面或动态代码加载路径。

## 3. 强约束

### 3.1 零功能删减

以下任一情况均视为发布阻断：

- 任一现有协议入口消失或无法保存、加载、生成配置、启动连接。
- 任一现有 JNI 方法、Java 绑定类、字段或方法签名缺失或不兼容。
- VPN、代理服务、订阅、分组、节点测速、URLTest、智能分流、路由规则、DNS、分应用代理、备份恢复、WebDAV、插件、设置、主题、语言或基础导航出现功能退化。
- 用户从 1.3.2 覆盖安装后丢失节点、订阅、分组、智能分流选择、路由规则、分应用名单或设置。
- 为通过构建而关闭协议、删除 build tag、删掉扩展依赖、屏蔽错误路径或回退到旧核心。
- 只验证应用能启动，却没有验证 VPN、核心版本和主要数据流。

### 3.2 最小改动

在所有兼容门槛通过后，APK 工程内允许的最小变化为：

1. 替换 `apktool_out/lib/arm64-v8a/libgojni.so`。
2. 将 `apktool_out/apktool.yml` 的 versionName 改为 `1.3.3`、versionCode 改为 `252`。
3. 仅在用户可见版本仍显示旧值时，修正现有版本读取路径，使其读取 `PackageInfo`；不得借此重写关于页。
4. 添加不进入 APK 的核心构建清单和验证记录。

不得顺手处理 1.2.4 审计中的其他安全项，不得重构 Smali，不得增加依赖，不得清理当前工作树中的既有修改和临时验证产物。

### 3.3 相同签名覆盖升级

- 1.3.3 必须使用与基线 1.3.2 相同的签名证书。
- 本次自用版本允许继续使用现有 Debug 证书，仅用于确保覆盖升级；不得把这项决定描述为正式发布安全实践。
- 无法获得相同签名时必须停止。卸载重装不能替代覆盖升级验证。

## 4. 方案选择

### 4.1 推荐方案：同源源码重建

以 NekoBoxForAndroid 官方 `libcore`、`libneko` 和 gomobile/JNI 构建链恢复与当前 AnyBox 同源的核心构建环境，在保持现有绑定、补丁和 build tags 的前提下，将 sing-box 上游基线更新到官方 `v1.13.19`，生成新的 `libcore.aar`，确认 Java/JNI API 完全兼容后提取 `arm64-v8a/libgojni.so`，替换到 1.3.2 apktool 工程并整包构建。

这是唯一默认执行方案。

### 4.2 受限备选：采用已发布的同源 `libcore.aar`

只有同时满足以下条件，Luna 才可使用 NekoBoxForAndroid 官方发布或官方 CI 生成的 `libcore.aar`：

- 可证明其核心基于官方 sing-box `v1.13.19`；
- 版本字符串以 `1.13.19` 开头；
- Java/JNI API 与当前 AnyBox 基线完全一致；
- build tags 和协议能力不少于当前基线；
- AAR 来源、下载 URL、发布 tag、SHA-256 和签名/校验信息可记录；
- 完整回归门槛全部通过。

来源不明、只有 APK、无法证明源码版本或 API 不一致时不得使用该备选。

### 4.3 禁止方案

- 直接下载官方 sing-box CLI 二进制并改名为 `libgojni.so`。
- 从官方 SFA APK、第三方客户端 APK 或不明压缩包提取 `.so` 后直接替换。
- 仅修改二进制中的版本字符串，实际仍运行旧核心。
- 在 Java 层启动外部 sing-box 可执行文件，建立与现有 libcore 并行的第二套核心。
- 在 App 私有目录动态下载和 `System.load()` 新核心。
- 为适配官方核心而删除 Neko/AnyBox 定制协议、插件桥接、配置字段或平台接口。

## 5. Luna 执行契约

Luna 开始实施时必须依次执行：

1. 读取 `.ai/HANDOFF.md` 和本文。
2. 执行 `git status --short --branch`，识别并保留所有既有修改。
3. 核对 1.3.2 APK、当前 `libgojni.so`、版本、签名、SHA-256 和模拟器状态。
4. 在独立临时目录或独立源码工作树恢复核心源码；不得把上游完整 Android 工程覆盖到当前 apktool 工程。
5. 先完成 Gate 0 和 Gate 1，再允许替换 APK 中的核心。
6. 每完成一道 Gate，立即更新 `.ai/HANDOFF.md`，写入实际命令、结果摘要和下一步唯一动作。
7. 任一停止条件触发时保留现场，记录最窄阻塞点，不尝试绕过门槛。

Luna 不得执行 `git reset --hard`、`git checkout --`、批量删除临时目录或覆盖用户工作树。不得把未验证结果写成“完成”。

## 6. Gate 0：源码恢复与可复现基线

### 6.1 优先查找现有源码

Luna 应先在本机可读范围查找以下候选：

- `Pskora` Android 工程及其 `libcore`；
- `sing-box` 本地源码；
- `libneko` 本地源码；
- NekoBoxForAndroid 源码或既有 `libcore.aar`；
- 能对应 `1.13.15-neko-1` 的构建脚本、补丁、Go module cache 或 Git worktree。

找到候选后必须记录仓库 URL、分支、commit、工作树状态、Go/Java/NDK/gomobile 版本和构建命令。不得把二进制中的 Windows 路径当作源码已经找到。

### 6.2 无本地源码时的恢复路径

若本地没有完整源码，允许从以下官方仓库恢复：

- `https://github.com/MatsuriDayo/NekoBoxForAndroid.git`；
- 该工程构建脚本明确引用的官方 `MatsuriDayo/libneko` 与 gomobile 仓库；
- `https://github.com/SagerNet/sing-box.git`。

必须在 NekoBoxForAndroid 历史中找到能生成 `1.13.15-neko-1` 或与当前 JNI 接口等价的源码节点。不能仅使用当前 main 并假设兼容。

### 6.3 基线重建证明

在升级到 1.13.19 前，先用恢复的源码构建一次 1.13.15 同线基线。字节级 SHA-256 不要求与旧 `.so` 相同，因为 Go BuildID、路径和工具链可能导致差异；但以下语义必须全部一致：

- `libcore.aar` 中 Java 包名、类名和所有 public/native 方法签名一致；
- `libcore.Libcore` 的全部现有 JNI 方法存在；
- build tags 不少于当前基线且没有移除现有 tag；
- ABI 仍包含 `arm64-v8a`；
- `versionBox()` 返回 `1.13.15-neko-1` 或可证明的同线版本；
- 核心能被最小测试 APK 或 AnyBox 基线加载，不出现 `UnsatisfiedLinkError`、`NoSuchMethodError`、`ClassNotFoundException`、`VerifyError`；
- 能生成并启动至少一个现有有效节点配置；
- Go 模块依赖仍包含当前 AnyTLS、Juicity、Mihomo、替换版 sing-vmess、替换版 sing-snell 和 Neko 平台绑定。

若无法完成基线重建证明，Gate 0 失败，Luna 必须停止。

### 6.4 构建清单

Gate 0 通过后，在项目的非 APK 交付目录生成一份核心构建清单，至少记录：

- 每个源码仓库的 URL 和完整 commit SHA；
- sing-box 官方基础 tag 与其解析后的 commit SHA；
- 叠加的 Neko/AnyBox 补丁 commit 或补丁文件 SHA-256；
- Go、Java、Android SDK、NDK、gomobile/gobind 版本；
- 完整 build tags；
- 构建命令；
- 生成的 `libcore.aar` 和 `libgojni.so` SHA-256。

清单不得包含密钥、密码、令牌或本地隐私路径。

## 7. Gate 1：升级到 sing-box 1.13.19

### 7.1 上游固定

- 获取官方 `SagerNet/sing-box` tag `v1.13.19`。
- 验证 tag 对应 commit，并记录到构建清单。
- 禁止 `go get ...@latest`，禁止更新到 1.14 预发布版本。
- 如果 Neko 构建通过 local replace 引用 sing-box，应让 replace 指向已固定 `v1.13.19` 基线并叠加必要兼容补丁；不得让构建结果继续显示来源不明的任意工作树。

### 7.2 保留定制能力

升级时必须保留：

- Neko `libcore` Android 平台接口和 gomobile Java 绑定；
- 当前 `with_gvisor,with_quic,with_wireguard,with_utls,with_clash_api` build tags；
- AnyTLS、Juicity、Mihomo、sing-vmess、sing-snell 和现有插件桥接；
- URLTest、Clash API、STUN、日志、连接重置、GeoIP/Geosite、解压和本地 DNS 接口；
- Android VPN、保护 Socket、本地 DNS 传输和网络变化监听；
- AnyBox 当前配置生成器所使用的全部 JSON 字段和协议选项。

若 1.13.19 要求依赖联动升级，只允许做编译和运行所必需的最小联动，并逐项记录版本变化。不得独立升级 Android Gradle Plugin、Kotlin、UI 库或 apktool 工程依赖。

### 7.3 JNI/API 等价检查

对基线 AAR 与 1.13.19 AAR 执行机器可比较的 API 清单，比较所有生成 Java 类、public 方法、native 方法、构造器、字段和包名。

通过条件：API 完全一致。仅底层实现和版本字符串发生变化。

若出现新增、删除或变更的 Java/JNI API，Luna 必须停止并报告差异；本轮设计不授权修改应用 Java/Smali 调用层来适配新 API。

### 7.4 核心身份检查

新核心必须同时满足：

- `versionBox()` 以 `1.13.19` 开头；
- 构建清单指向官方 `v1.13.19` commit；
- `go version -m` 输出与固定源码和依赖一致；
- 新 `libgojni.so` SHA-256 与 1.3.2 基线不同；
- 不含 `1.14.0-alpha`、`beta`、`rc` 标识；
- AnyTLS 官方隐私修复存在；
- ARM64 ELF 可被 Android 15 基线设备加载；额外执行 16 KiB page-size 对齐检查并记录实际结果，但本轮不以新增 16 KiB 设备支持为目标。只有目标自用设备实际采用 16 KiB page size 时，该检查失败才是发布阻断。

## 8. APK 集成设计

### 8.1 集成边界

Gate 0 和 Gate 1 通过后：

1. 从已验证的 1.13.19 `libcore.aar` 提取 `arm64-v8a/libgojni.so`。
2. 替换 `apktool_out/lib/arm64-v8a/libgojni.so`。
3. 不替换 `libandroidx.graphics.path.so`。
4. 不改 `go/Seq.smali`、`libcore/*.smali` 或应用调用代码，因为 Gate 1 已要求 API 完全一致。
5. 设置 versionName `1.3.3`、versionCode `252`。
6. 保持 package、minSdk、targetSdk、ABI、权限、组件、资源、数据库和偏好键不变。

### 8.2 构建与签名

- 使用当前项目适配的 apktool 3.x 强制全量构建。
- 对未签名 APK 执行 zipalign。
- 使用与 1.3.2 相同的签名证书签名。
- 对最终 APK 执行 `apksigner verify --verbose --print-certs`。
- 使用 aapt2 核对 package、versionName、versionCode、minSdk、targetSdk 和 ABI。
- 最终文件名固定为 `AnyBox-1.3.3.apk`，不得带 `debug`、`test`、`final2` 或日期后缀。

### 8.3 静态差异门槛

最终 APK 与 1.3.2 基线的预期变化仅限：

- `lib/arm64-v8a/libgojni.so`；
- 版本元数据及由重新打包产生的签名/ZIP 元数据。

若资源、Manifest 组件、DEX/Smali、数据库 schema、偏好 XML、资产或其他 native library 出现非版本性差异，Luna 必须解释来源并停止发布，除非差异是 apktool 重打包的可证明无行为变化结果。

## 9. Gate 2：构建与静态验证

以下检查必须全部有实际输出：

1. `git diff --check` 通过。
2. apktool 强制全量构建成功。
3. zipalign 校验成功。
4. apksigner v1/v2/v3 验证通过。
5. 签名证书 SHA-256 与 1.3.2 完全一致。
6. aapt2 显示 `com.zane.proxy`、`1.3.3 (252)`、minSdk 23、targetSdk 35。
7. APK 只包含预期 ABI，不意外删除 `arm64-v8a`。
8. `libgojni.so` ELF、Go 构建信息、build tags 和核心版本检查通过。
9. 基线与新 AAR 的 Java/JNI API 清单完全一致。
10. 最终 APK ZIP 完整性检查通过。
11. 记录 APK 大小、SHA-256、核心 SHA-256、AAR SHA-256 和构建清单路径。

任何检查失败都不能进入 Gate 3。

## 10. Gate 3：覆盖升级与运行验证

### 10.1 1.3.2 数据基线

在隔离的 Android 15/API 35 ARM64 模拟器中安装已验证的 1.3.2，并建立至少包含以下内容的真实基线数据：

- 一个可联网的有效订阅；
- 至少两个不同延迟的有效节点；
- 一个自动选择最低延迟的完整分组；
- 智能分流内置组、自定义组、应用选择和自定义规则源；
- 用户高优先级路由规则和普通路由规则；
- 分应用代理/绕过名单；
- DNS、Mixed Inbound、Clash API、自动更新时间、URLTest 周期和容差设置；
- 至少一次备份文件。

安装前后导出不含凭据的数据库计数、设置摘要和 UI 截图，用于确认数据保留。

### 10.2 覆盖升级

- 使用系统正常覆盖安装路径从 1.3.2 安装 1.3.3，不清数据、不卸载。
- 安装后核对 package、versionName、versionCode、签名和核心版本。
- 冷启动和后台进程启动均不得出现 JNI 或核心加载异常。
- 节点、订阅、分组、智能分流、路由规则、分应用名单和设置必须全部保留。

### 10.3 核心生命周期

逐项验证：

- VPN 首次连接、断开、重连；
- 切换节点和切换分组；
- 配置 reload；
- 飞行模式或网络切换后的恢复；
- 应用退到后台再返回；
- 锁屏/待机至少 30 分钟后连接仍可用；
- 服务被系统回收后的可理解恢复行为；
- 重启应用后核心正常初始化；
- URLTest、STUN、Clash API 和连接重置接口可调用。

日志必须检查 native crash、SIGABRT、`UnsatisfiedLinkError`、`NoSuchMethodError`、`ClassNotFoundException`、`VerifyError`、`FATAL EXCEPTION`、ANR 和重复加载异常。

## 11. 协议兼容回归矩阵

### 11.1 验证原则

“界面还在”不等于协议正常。每个现有协议至少必须验证：

1. 新建或导入配置；
2. 保存后重新打开字段不丢失；
3. 生成核心配置成功；
4. 核心实例创建成功且无未知字段/未知协议错误；
5. 通过真实服务器或可控本地测试服务完成 TCP；支持 UDP 的协议还要完成 UDP；
6. 测速、连接、断开和重连正常。
